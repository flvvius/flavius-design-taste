# Search state and a reading fallback

Cycle 23 reviews the asynchronous library example after chart values joined the maintained browser suite. The earlier search review covered six layouts and reported no actionable asynchronous defect. The new work checks five visible states across all maintained variants and engines, and examines what remains usable without scripts.

## Adobe source review

Reviewed [React Spectrum's `useAsyncList.ts`](https://github.com/adobe/react-spectrum/blob/740c6c5c4a717ca8c82fc4d15d199f6166cd42dc/packages/react-stately/src/data/useAsyncList.ts) at revision `740c6c5c4a717ca8c82fc4d15d199f6166cd42dc`. Its reducer ignores success and error actions when their request controller differs from the one currently stored in state. A replacement request can abort the old controller. The [published guide](https://react-aria.adobe.com/useAsyncList) describes loading, errors, filtering, sorting and abortable requests.

The portable lesson is to connect results and errors to the request that produced them. Cancellation can save work; the identity check still protects the current state. The local example already uses a generation counter at both completion paths and invalidates work before debounce. This study preserves that behavior and adds maintained checks. It does not introduce React, a fetching library or a live service.

## Observable states and controlled time

[W3C status-message guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) explains why result counts, waiting and error messages need programmatically available status. The example already places its status outside the busy result region. The checker observes that structure and the visible query, message, result titles, loading state and retry action together. Actual announcements still require screen-reader testing.

The [Playwright clock guide](https://playwright.dev/docs/clock) distinguishes fixed dates from controlled timers. These tests install the clock before navigation, pause before interaction and advance timers explicitly. That allows the waiting, loading, completed and obsolete-response states to be checked separately without timing the host machine. The harness checks native keyboard reading and retry focus too.

A deliberate fixture removes the two completion guards. The same sequence passes on the healthy example and rejects that mutation when the slow request replaces the current climate results. The fixture checks the obsolete request's actual status and titles, rather than accepting an unrelated assertion failure. It also verifies author and title queries after the healthy topic-search sequence.

## Composition evidence

The [event probe](../cycles/23/before/composition-probe.json) found an important test difference. Firefox's `fill()` emitted its own composition start and end events. Filling after a synthetic start therefore ended composition before the test expected it to end. The application correctly returned results after that end event. Chromium and WebKit did not emit the same sequence.

The corrected simulation updates the value and dispatches an input event marked as composing, then dispatches submission without ending composition. It checks that searching remains deferred, pending work cannot reappear, and ending composition starts the current query. This is a browser event simulation, not evidence for an operating-system input method. The existing product guard did not need a change.

## Reading when enhancement is unavailable

The [script-disabled baseline](../cycles/23/before/no-script.json) had no titles, no status explanation and three enabled search controls. Six small bundled records now live in ordinary HTML rows with native disclosures. Enhancement reads those records, initializes filtering and enables the controls. The script-disabled instructions describe reading, and the enhanced instructions describe searching.

This is appropriate for a small local collection. A remote or large corpus can require a service and a different unavailable state. The shared taste records that distinction instead of requiring every search interface to ship all records. No dependency or API is added to the portable skill.
