# Principles

These rules reuse the existing directions and interpret the two own-work projects. Origin labels separate source observations, inherited guidance and inference. Examples describe actual decisions; anti-examples illustrate rejected alternatives.

## 1. Begin with the person and task

Origin: Inference from both own-work projects; inherited from both review guides.

Reason: A subject gives the composition a reason.

Applies: New pages and substantial redesigns.

Limits: A small spacing correction does not need a new concept.

Example: Pricele makes a price the reveal; portfolio links named work through familiar objects.

Anti-example: A generic growth hero on an unrelated settings screen.

## 2. Assign type roles before choosing decoration

Origin: Observed in both own-work projects; the generalized instruction is an inference.

Reason: Hierarchy lets readers find the action and distinguish prose from figures.

Applies: Every screen with several content roles.

Limits: One font can serve several roles; do not force three families.

Example: Schoolbell uses size; Pricele uses Instrument Serif, Archivo and IBM Plex Mono.

Anti-example: Six arbitrary weights and fonts without a reading hierarchy.

## 3. Give ordinary content the page background

Origin: Observed in both projects; inherited from both directions.

Reason: Spacing and rules can explain groups without repeating chrome.

Applies: Reading, settings, repeated rows and page sections.

Limits: An overlay, selectable option, game figure or material note can earn a surface.

Example: Pricele reference sections use rails; portfolio notes use material surfaces.

Anti-example: A card inside a card around every paragraph.

## 4. Use alignment to explain relationships

Origin: Observed in both projects; practical interpretation is an inference.

Reason: Shared edges make content easier to compare.

Applies: Lists, tables, reading layouts and object collections.

Limits: A single note can overhang a grid when the text remains readable.

Example: Pricele heading rail and portfolio twelve-column composition.

Anti-example: Unrelated centered blocks with inconsistent row anatomy.

## 5. Spend expressive color deliberately

Origin: Observed in both projects; budget as a rule is an inference.

Reason: A signal remains useful when everything else does not compete with it.

Applies: Brand accents and emphasis.

Limits: Labeled game temperature, chart series and warning colors can use more hues.

Example: Portfolio orange underline; Pricele vermilion alongside a meaningful temperature ramp.

Anti-example: Blue, violet, green and orange assigned to ordinary feature cards for variety.

## 6. Separate essential boundaries from quiet separators

Origin: Inherited from Editorial calm contrast fixes; not claimed as observed shared DNA.

Reason: A pale hairline can group content while an input still needs identification.

Applies: Controls, focus and separators in every palette.

Limits: Decorative separators need not satisfy the essential-boundary threshold.

Example: Use input for a field and border for a section rule.

Anti-example: Use a faint decorative border as the only sign of an editable field.

## 7. Let density follow the activity

Origin: Observed in portfolio and Pricele; generalized instruction is an inference.

Reason: Reading, scanning and frequent commands need different space.

Applies: Mixed-content products and responsive layouts.

Limits: Do not apply portfolio section gaps to dense operator tools.

Example: Pricele compact game beside wider methodology pages.

Anti-example: A 160px gap between every setting or twelve tiny tiles on a personal page.

## 8. Choose one subject-specific visual idea

Origin: Inference from both projects; inherited from Personal room.

Reason: A coherent idea gives personality without multiplying effects.

Applies: A new opening or a substantial visual direction change.

Limits: A functional screen can use type and layout alone.

Example: A listening bar for the portfolio; a newspaper edition for Pricele.

Anti-example: A gradient globe, unrelated mascot and floating dock in one hero.

## 9. Keep controls conventional and words precise

Origin: Inherited from both directions; source examples support it, but this is a workflow rule.

Reason: Visitors should not need to decode the visual metaphor to act.

Applies: Forms, navigation, errors and destructive actions.

Limits: Casual labels can suit a personal destination when its meaning remains apparent.

Example: Label a work object and retain an ordinary destination.

Anti-example: An unlabeled clickable illustration or a submit button called Make magic.

## 10. Adapt composition while retaining the task

Origin: Observed in both projects; behavior checks inherited from v1.

Reason: Narrow screens need their own usable arrangement.

Applies: Mobile, long content, localization and enlarged text.

Limits: A dense comparison table may keep a labeled scroll region.

Example: Portfolio shelf becomes named links; Pricele rails become a vertical stack.

Anti-example: Shrink all text or hide key actions to preserve the desktop composition.

## 11. Make motion explain state or a meaningful object

Origin: Observed in both projects; inherited direction limits remain specific.

Reason: Feedback should clarify what changed and tolerate interruption.

Applies: Control feedback, overlays and optional illustration.

Limits: A drawing may be longer than Editorial calm feedback. Reduced motion preserves all content.

Example: Portfolio optional 600ms scribble versus Pricele 140ms press.

Anti-example: Repeated reveal animations on every frequently used navigation command.

## 12. Verify the rendered result and preserve behavior

Origin: Inherited from v1 review guidance and evaluation failures, not aesthetic DNA.

Reason: A green build cannot establish a usable screen or an intact interaction.

Applies: Delivery of an audit, redesign or new page.

Limits: State unverified conditions rather than requiring unavailable platform certification.

Example: Recheck focus, actual contrast, 200% text and the behavior contract after changes.

Anti-example: Declare a redesign done from classes, screenshots of an empty shell or a success toast alone.
