# Redesign an existing app

Start with discovery, behavior boundaries and baseline capture. Use the ranked audit to choose the most useful representative screen. Select an existing direction or document a project-specific variant. A client's existing brand can determine the accent and type; preserve the shared hierarchy and purpose of surfaces.

Write the implementation plan with affected files and states, intervention level, expected regression checks and known limits. Use the smallest coherent batch that a reviewer can inspect. Do not mix token polish with new navigation behavior silently.

Get one screen right before extending. Compare its actual render with the baseline. Check the main action, row anatomy, density, long content and mobile arrangement. If autonomous implementation is authorized, record the decision and proceed; a request for another approval would add no protection.

Apply in order:

1. Semantic tokens and type roles. Change the existing source, regenerate exports and inspect every consumer affected by global values.
2. Layout, grouping and component anatomy. Keep behavior bindings, IDs, routes, query parameters, accessibility semantics and data boundaries.
3. Copy. Keep facts and event meaning. Change functional labels only when they still describe the same action.

Extend the proven anatomy to the remaining authorized screens. Preserve product differences rather than forcing one page template everywhere. Check shared components in every relevant context.

Each commit or PR states the trigger/problem, resulting behavior, intervention level, before/after, rationale, test results and limitations. Recapture the baseline matrix, execute the behavior contract and re-score the rubric before handoff. If a visual change exposes a pre-existing behavior defect outside scope, record it; do not quietly replace the flow.
